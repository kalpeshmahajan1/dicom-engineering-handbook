1. Start with the mental model

Imagine two radiology systems talking to each other. One system says: “Give me this CT study.” Another says: “Store this CT image.” These are operations performed over a DICOM association.

DIMSE

The DICOM Message Service Element is the command-oriented communication mechanism traditionally used over a DICOM network association.

Operation

An operation is an action such as C-STORE, C-FIND, C-MOVE, N-ACTION or N-GET.

Dataset

Patient/study/image attributes and sometimes Pixel Data are carried as a DICOM dataset associated with a command.

Illustrative—not a byte-level packet capture.

Important: “Composite” does not mean “multiple network messages combined together.” It refers to a Composite IOD/instance containing information about multiple aspects of a real-world entity. “Normalized” refers to a different modeling style in which attributes and operations are treated more independently.

2. Composite operations — learn them through one CT study

A Composite Instance brings together attributes that describe a real-world object at several levels. A CT image can contain Patient, Study, Series and Image-level information in one instance. The operation generally treats that instance as a whole DICOM object.

Example: C-STORE

A modality or gateway wants PACS to store a CT image. The SCU sends a C-STORE-RQ. The receiver (SCP) processes the request and returns C-STORE-RSP with a status.

SCU → C-STORE-RQ + CT DICOM Dataset → SCP SCP → C-STORE-RSP + Status → SCU

C-FIND: “Tell me which objects match this query”

C-FIND is commonly used for query/retrieve workflows. The SCU sends query keys. The SCP may return zero, one, or many pending responses, followed by a final response.

C-FIND-RQ (PatientID=123, StudyDate=20260930) ↓ C-FIND-RSP Pending → Study A C-FIND-RSP Pending → Study B C-FIND-RSP Pending → Study C C-FIND-RSP Final → Success

The key learning point is that “response” does not necessarily mean “finished.” A pending response can carry another matching dataset.

3. Normalized operations — think “object management API”

Normalized services are easier to understand if you imagine an object-oriented API. Instead of primarily moving a complete Composite Instance, the operation can target a managed object and perform a defined operation on it.

OperationPlain EnglishAnalogy
N-GETRead specified attributes of a managed object.GET /object/attributes
N-SETChange specified attributes.PATCH /object
N-ACTIONRequest a defined action.POST /object/action
N-CREATECreate a managed object.POST /objects
N-DELETEDelete a managed object.DELETE /object
N-EVENT-REPORTReport an event occurring to/with an object.Event notification/webhook
Do not over-generalize: DICOM normalized operations are not literally REST APIs. REST is only a teaching analogy. The actual semantics, command fields, SOP Classes and status behavior are defined by DICOM.

Example: N-GET

Suppose a defined DICOM service provides a managed object whose attributes can be read. The requester identifies the object and asks for selected attributes.

N-GET-RQ Requested SOP Class UID Requested SOP Instance UID Attribute Identifier List ↓ N-GET-RSP Status Attribute List (if successful)

The important contrast with C-STORE is that N-GET is fundamentally asking for attributes of a managed object rather than transferring a complete image instance as the primary operation.

Example: N-ACTION

N-ACTION is useful when a DICOM-defined object exposes a meaningful action. The requester supplies an Action Type ID and, where defined, an action information dataset.

Requester: “Perform Action #1 on this object.” ↓ N-ACTION-RQ ↓ Provider: performs defined action ↓ N-ACTION-RSP + Status + optional response dataset

4. What actually happens on the wire?

Freshers often imagine a DIMSE operation as one packet. It is better to visualize it as a command exchange plus optional datasets, carried inside a DICOM Upper Layer association.

LayerRole
Application semanticsC-STORE, C-FIND, N-GET, N-ACTION, etc.
DIMSE commandIdentifies request/response, SOP class, message ID, status and other command fields.
DICOM datasetAttributes associated with the command, depending on the operation.
Presentation contextNegotiated SOP Class + Transfer Syntax combinations.
AssociationNegotiated communication relationship between two DICOM AEs.
TransportTraditionally TCP; TLS can be used for secure transport.

Request/response IDs

Many DIMSE request commands contain a Message ID. The corresponding response identifies the request through a related Message ID. This lets implementations correlate responses with outstanding operations.

Developer rule: Do not build application logic around “the next message is always the response.” Correct implementations understand DIMSE command semantics, message identifiers, pending/final statuses, and the possibility of multiple responses.

5. Service classes: where operations get their meaning

An operation by itself is not enough. A DICOM Service-Object Pair (SOP) Class combines a defined object model with a set of permitted operations/notifications. The same operation name can have different semantics depending on the SOP Class specification.

6. End-to-end examples

Example A — CT scanner sends an image

  1. Scanner and PACS establish an association.
  2. They negotiate presentation contexts.
  3. Scanner sends C-STORE-RQ with the CT image dataset.
  4. PACS validates/processes/stores the object.
  5. PACS sends C-STORE-RSP with status.

Example B — Viewer searches for a patient's studies

The viewer sends C-FIND-RQ with query keys. PACS can return multiple pending C-FIND responses, each carrying a matching dataset, and finally a final C-FIND response.

Example C — Viewer retrieves a study using C-MOVE

The viewer asks PACS to move matching instances to the viewer's AE. PACS then initiates storage operations toward the move destination. This is why C-MOVE is not simply “download this file.” It is a coordinated DICOM service operation.

Example D — Normalized operation concept

Imagine a managed DICOM object with defined attributes and actions. An N-GET reads attributes, N-SET changes permitted attributes, and N-ACTION requests a defined action. The exact permitted attributes and semantics are determined by the relevant SOP Class.

7. Fresher developer checklist

1. Identify the SOP Class

Never interpret a command only from its name. Determine which SOP Class is being used.

2. Identify SCU/SCP

Ask who is invoking the service and who provides it.

3. Separate command from dataset

The command tells you what is happening; the associated dataset carries operation-specific content.

4. Handle status correctly

Success, warning, failure and pending statuses have different meanings depending on the operation.

5. Expect multiple responses

C-FIND and retrieval operations can involve multiple pending responses/sub-operations.

6. Respect negotiated transfer syntax

The association negotiation determines how datasets are encoded and transferred.

Composite vs normalized: interview-ready explanation

Short answer: “Composite DIMSE operations are centered around operations on composite DICOM instances, such as storing, querying and retrieving imaging objects. Normalized DIMSE operations are centered around manipulating or invoking behavior on defined managed objects and their attributes, using operations such as N-GET, N-SET, N-ACTION, N-CREATE and N-DELETE.”

Better answer: “The distinction is about the DICOM information model and service semantics, not merely about message size. Composite objects combine related information into a single instance, while normalized services expose operations that address object attributes and defined behavior more independently. The actual semantics always come from the relevant DICOM SOP Class.”

8. Self-check quiz

Q1. Does C-FIND always produce exactly one response?

No. It can produce multiple pending responses followed by a final response.

Q2. Is N-GET the same as downloading a DICOM image?

No. N-GET retrieves defined attributes of a managed object. Image retrieval is a different service scenario.

Q3. Is “Composite” synonymous with “multiple network packets”?

No. Composite describes the DICOM information/object model; packetization is a lower-level transport/presentation concern.

Q4. What does SCU mean?

Service Class User—the AE invoking the service.

Q5. Why can C-MOVE result in C-STORE activity?

Because the requested retrieval is performed by moving matching instances to the specified destination, commonly using C-STORE sub-operations.
