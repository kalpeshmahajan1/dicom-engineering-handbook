What DICOM overlays are

Meaning

An overlay plane is a 1-bit-per-pixel bitmap stored beside the image in repeating groups 6000–601E (even groups, up to 16 planes per object). A set bit means “draw here”; a clear bit means “leave the image visible”. It carries no grey values, only a mask.

Need

Annotations burned into pixel data destroy diagnostic information and cannot be hidden. Overlays keep pixels untouched while still letting the modality or a workstation attach markers, ROIs, patient orientation letters, scale marks or graphics.

Significance

The image stays original and lossless-comparable, the annotation is toggleable, and both travel in one object with the same SOP Instance. Viewers must still honour them: a missed overlay can hide a technologist’s or CAD’s marker.

Usage

Ultrasound and CR text, CAD marks, ROI outlines from acquisition stations, segmentation-like masks in legacy data, DR collimation shutters as graphics, and teaching-file arrows. New work should prefer GSPS, SEG or SR, but PACS/VNA still receive 60xx data daily.

How Overlay Data relates to Pixel Data

Pixel Data (7FE0,0010) is described by the Image Pixel Module: Rows, Columns, Bits Allocated, Bits Stored, High Bit, Pixel Representation and Photometric Interpretation. Overlay Data (60xx,3000) has its own Rows/Columns, so an overlay may be smaller than the image and is positioned by Overlay Origin.

Bits are packed least-significant bit first, row after row with no row padding. Pixel n of the overlay (row-major, 0-based) is bit n mod 8 of byte n div 8. Example for eight pixels 1 0 1 1 0 0 0 1:

10110001

The first pixel goes into bit 0, so writing the byte from bit 7 down to bit 0 gives 10001101₂ = 0x8D.

const on = (data[n >> 3] >> (n & 7)) & 1;   // decode pixel n
data[n >> 3] |= 1 << (n & 7);               // encode pixel n
Retired: overlays embedded in Pixel Data

Older objects set Overlay Bits Allocated = 16 and store the mask in unused high bits of each pixel word (e.g. Bits Stored 12 leaves bits 12–15). Overlay Bit Position tells you which. Modern viewers should still mask those bits off before window/level or the overlay corrupts the grey values.

Rendering pipeline used on this page

1) Parse with dicomParser. 2) Build a Cornerstone image with stored values, rescale slope/intercept and VOI window. 3) Enumerate 60xx3000 elements, unpack bits, colour them, cache as bitmaps. 4) On every cornerstoneimagerendered event, place each bitmap on its own canvas using cornerstone.pixelToCanvas and the viewport scale, so pan/zoom stay aligned.

Common pitfalls

Treating Origin as 0-based; padding rows to bytes; forgetting even-length padding; ignoring Overlay Type R vs G; applying VOI LUT to overlay pixels; assuming all overlays are on frame 1; flipping overlays when the image is flipped or rotated.
